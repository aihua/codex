# 版本管理 — 本地 Codex 形态

> **执行方式：** 版本管理**完全由本 Skill + 本地 git 实现**；没有云端版本
> 服务，没有云端推送工具。Agent 在 Codex 启动时的本地工作目录（下称"工作
> 区根目录"）内执行 git 与文件操作；每产生一个新版本，用**对话内版本卡
> 片**向用户报告（`send_file` 的本地等效替换，格式见 §3.4）。

> **对用户沟通规则：** 版本管理的技术细节（git 命令、meta.json 更新、版
> 本号计算等）是内部执行过程，禁止在对话中向用户展示或提及。用户只需看
> 到：生成结果 + 一行版本卡片。如需告知版本信息，只说"已保存为 V{n}"，
> 不解释底层操作。

## ⚠️ 路径硬规则（最高优先级，写任何文件之前先执行本节）

**本 Skill 必须在写出第一个入口文件之前介入，而不是产出之后补救。** 任
何入口文件（`.html` / `.jsx` / `.tsx` / `.vue`）第一次写入磁盘时，目标路
径就必须位于 `我的项目/{项目名}/` 内。

### 基准路径

「我的项目」**固定位于工作区根目录**（Codex 启动时的 cwd，本地绝对路径形
如 `/data/repo/web/我的项目/`）。执行任何 `mkdir` / `cd` / 写文件操作之
前，必须先回到工作区根目录（或使用从根目录起算的完整路径）；**禁止**在
未确认 `pwd` 的情况下使用相对路径 `我的项目/...`——这是「我的项目」文件
夹长在错误位置的常见原因。

### 写文件前的固定顺序（不可调换）

```bash
# 1. 确定项目名（生成规则见 references/project-conventions.md）
# 2. 回到工作区根目录，创建项目目录
cd {工作区根目录}
mkdir -p "我的项目/{项目名}/assets"
# 3. 进入项目目录，之后所有文件【直接】在此目录内创建
cd "我的项目/{项目名}"
# 4. 写入 index.html / prototype.html 等入口文件与代码文件
# 5. 再进入本文件 §3 / §4 的 git / meta.json / 版本卡片流程
```

### 违例清单（以下任何一种都算流程错误，即使事后移动也算）

- 先把文件写到工作区根目录、`~/Desktop`、`/tmp` 或当前任意目录，再移动
  进项目目录
- 只在对话中贴代码块，不落盘
- 在项目目录之外执行写文件命令

### 写文件前自检（最后一道闸）

调用任何写文件命令之前，自问一句：**「我即将写入的目标路径，是否位于
`我的项目/{项目名}/` 之内？」** 答案不是 → 停止，先执行上面的固定顺序建
目录，再写文件。

## 1. 触发判断

产出物包含以下类型的前端文件：`.html`、`.jsx`、`.tsx`、`.vue` → **必须**
创建/更新项目并走版本流程（与任务是否经过设计路由无关）。

产出物是 image、doc、ppt、JSON、design spec、纯文本等 → 普通文件，不创建
项目，不触发本 Skill。

**常见误判（禁止）：** 因路由到某个设计场景就认为「只贴代码块」或「写
Desktop 即可」；凡写出入口 HTML/前端文件即按项目交付。

与设计同插件技能（glm-visual-design-foundations / glm-ui-ux-pro-max）的协
同衔接、目录结构与资源落点细则、多项目管理，见
`references/project-conventions.md`（按需读，默认不读）。

## 2. 项目创建（首次）

首次为用户产出入口文件时（**第 1–3 步必须发生在写出任何代码文件之
前**，见顶部「路径硬规则」）：

1. 根据用户意图生成语义化中文或英文项目名称（如 `北京旅游网站`）
2. 回到工作区根目录；若「我的项目」不存在：`mkdir -p 我的项目/`
3. 创建项目目录与 assets：`mkdir -p 我的项目/{项目名}/assets`，然后
   `cd` 进入，**所有文件直接在此目录内写出**
4. 用户提供的图片先落到 `assets/`（来源与三种资源形态的处理规则见
   `references/project-conventions.md` §2），再写 HTML；禁止只写
   `assets/` 路径不落盘
5. Git 初始化与首次提交：

```bash
cd 我的项目/{项目名}
git init
echo -e "meta.json\nstyle-samples*.html" > .gitignore
git add .
git commit -m "V1: {一句话摘要}"
git tag v1
# ↑ 以上必须全部执行完，然后创建 meta.json，最后输出版本卡片
```

6. 创建 `meta.json`（完整结构与字段表见 `references/version-operations.md`）
7. 向用户输出版本卡片（§3.4），一行：「已保存为 V1」+ 主入口本地绝对路径

## 3. 版本管理

### 3.1 编辑入口与版本确定（本地形态）

| 编辑入口 | 项目 | 版本 |
|---------|------|------|
| 自然语言（对话框输入） | 见下方规则 | 见下方规则 |
| 「基于「{项目名}」V{n}版本进行编辑」句式 | 句式中的项目名 | 句式中的版本号（走 §4.4 合并流程） |

原宿主预览区的评论编辑、参数编辑器、对话流卡片按钮在本地 Codex 不存在；
其等效入口就是用户自然语言——用户直接说出项目名与版本号（推荐句式：
**「基于「{项目名}」V2版本进行编辑」**），处理规则与原评论/参数编辑完
全一致：指定版本 = 最新版本 → 直接编辑走 §3.3；指定版本 ≠ 最新版本（历
史版本）→ **必须**按 §4.4 合并流程执行，**禁止跳过恢复步骤**。

**自然语言默认：编辑最新项目的最新版本。不追问。** 确定项目优先级：
用户指名 > 本 session 最近操作 > 扫描 `我的项目/` 子目录读各项目
`meta.json` 后追问。

### 3.2 创建版本的时机

| 触发场景 | 是否生成新版本 | 说明 |
|--------|-------------|------|
| 首次生成 | ✅ V1 | 项目创建 |
| 自然语言编辑 | ✅ | 版本号递增 |
| 「基于「{项目名}」V{n}版本进行编辑」 | ✅ | §4 合并，产生一个版本 |
| 版本恢复 | ✅ | 见 §4 |
| 用户仅提供资源、无代码变更 | ❌ | 只写 `assets/`，不 commit |
| 用户提供资源且更新了代码引用 | ✅ | 须 commit + 版本卡片 |
| 在同项目下新增入口文件（如新增 `light.html`） | ✅ | 新文件与现有文件一起提交为新版本 |
| 小样阶段产出 `style-samples*.html` | ❌ | 不进 Git、不计版本号，仅吐卡片供用户选择 |

### 3.3 创建版本的 Git 指令

修改完成后，在项目目录执行：

```bash
cd 我的项目/{项目名}
LATEST_TAG=$(git tag --sort=-v:refname | head -n 1)
NEXT_NUM=$((${LATEST_TAG#v} + 1))
NEXT_TAG="v${NEXT_NUM}"
git add .
git commit -m "V${NEXT_NUM}: {一句话摘要}"
git tag $NEXT_TAG
# ↑ 以上必须全部执行完，然后更新 meta.json，最后输出版本卡片
```

### 3.4 对话流输出（send_file 的本地等效）

每生成一个新版本，必须输出版本卡片（**纯对话内容，不调用任何工具**）。
用户只需要知道两件事：存成了第几版、文件在哪里。

本地版本卡片格式（单入口项目默认）：

```text
已保存为 V3
项目「北京旅游网站」入口：/绝对路径/我的项目/北京旅游网站/index.html
```

- 第一行固定「已保存为 V{n}」，不解释底层操作
- 第二行给出主入口文件的**本地绝对路径**（用户浏览器直接 file:// 打开）
- 禁止在对话或源码中输出任何云端/OSS/CDN URL——本地交付没有线上地址

多入口文件项目、prototype 双文件交付、固定图片导出项目（export/ 目录）
的卡片策略与 commit 纪律，见 `references/version-operations.md`（按需
读）。默认只吐主入口；prototype 双交付对同一版本号连续吐两张卡片。

## 4. 版本恢复

### 4.1 恢复范围

恢复是**整个项目目录状态的恢复**（代码文件 + `assets/` 资源 +
`export/` 产物）。`git checkout` 还原目标版本的完整工作树，确保恢复后的
版本本地可完整打开。

### 4.2 恢复入口

| 入口 | 说明 |
|------|------|
| 自然语言「恢复到 V2」 | 直接执行 §4.3 标准恢复 |
| 自然语言「基于 V2 改风格」 | 执行 §4.4 合并流程（恢复 + 编辑 = 一个版本） |
| 「基于「{项目名}」V{n}版本进行编辑」句式 | 按 §4.4 合并流程处理 |

### 4.3 标准恢复（仅恢复，不附带编辑）

恢复 = checkout + 提交新版本 + 版本卡片，三步缺一不可。仅执行 checkout
不算恢复完成。执行指令：

```bash
cd 我的项目/{项目名}
TARGET_TAG="v{用户指定的版本号}"
LATEST_TAG=$(git tag --sort=-v:refname | head -n 1)
NEXT_NUM=$((${LATEST_TAG#v} + 1))
NEXT_TAG="v${NEXT_NUM}"
git checkout $TARGET_TAG -- .
git add .
git commit -m "V${NEXT_NUM}: 恢复至 V{目标版本号}"
git tag $NEXT_TAG
# ↑ 以上必须全部执行完，然后更新 meta.json，最后输出版本卡片
```

恢复后向用户确认：当前项目名和新版本号、包含哪些文件/页面、相比恢复前
的差异（如"不包含美食推荐板块，该功能在 V3 中添加"），并输出版本卡片。

版本编号始终递增（V4 恢复到 V2 → 产生 V5）。原有版本保留。

### 4.4 恢复 + 编辑合并流程（只产生一个版本）

适用：用户指定基于历史版本编辑（含「基于「{项目名称}」V{n}版本进行编
辑」句式）。

**版本号规则：** 无论基于哪个历史版本编辑，新版本号**必须**是当前最新
版本 +1 的纯数字递增（如当前 V8 → 新版本 V9）。**禁止**使用带后缀的版
本号（如 `V4-light`、`V4-dark`、`V2-new` 等），禁止以基准版本号为前缀
命名。**禁止**覆盖、移动或删除已有版本的 tag——已有版本永远保留，新版
本只能追加。

```bash
cd 我的项目/{项目名}
TARGET_TAG="v{目标版本号}"
git checkout $TARGET_TAG -- .
# ↓ 在此基础上执行用户请求的编辑（修改文件内容），不做中间 commit
LATEST_TAG=$(git tag --sort=-v:refname | head -n 1)
NEXT_NUM=$((${LATEST_TAG#v} + 1))
NEXT_TAG="v${NEXT_NUM}"
git add .
git commit -m "V${NEXT_NUM}: 基于 V{目标版本号}：{编辑内容摘要}"
git tag $NEXT_TAG
# ↑ 以上必须全部执行完，然后更新 meta.json，最后输出版本卡片
```

## 5. Hard rules

1. **第一个入口文件落盘前必须已建好 `我的项目/{项目名}/`**——文件直接写
   进项目目录，不是事后移动；只贴代码块不落盘视为未交付。
2. **提交门禁**：commit 前跑 `references/project-conventions.md` §3 的
   路径门禁与资源校验（项目内至少一个入口文件；工作区无散落入口文件；
   HTML 里的 `assets/` 引用全部有对应磁盘文件）——任一 ERROR / STRAY /
   MISSING → 先纠正再重跑门禁。
3. **版本卡片纪律**：每个新版本恰好一张卡片（prototype 双交付除外，两
   张）；只说「已保存为 V{n}」+ 主入口绝对路径，禁止展开 git/meta 细节。
4. **恢复必须 checkout 到位再编辑**：基于历史版本编辑时禁止跳过
   `git checkout $TARGET_TAG -- .`，无论认为差异多小。
5. **tag 只增不改**：禁止覆盖/移动/删除已有 tag；版本号禁止后缀命名。
6. **资源引用零悬空**：禁止 HTML 写 `assets/xxx` 而磁盘无对应文件；用户
   已引用的图片在新版本中未要求去掉就保留（`git add .` 自动复用，无需手
   动处理）。

## 6. 操作速查

| 用户行为 | 执行动作 |
|--------|--------|
| 「做一个 XX 网站」 | **先建** `我的项目/{项目名}/` → 目录内生成文件 → §2 创建（git init + V1）→ 版本卡片 |
| 「做一个产品原型（prototype）」 | **先建**项目目录 → 生成 `prototype.html` + `flow.html` → 同版 commit → 按双文件卡片（references/version-operations.md §3） |
| 「把标题改大一点」（无特殊上下文） | 编辑最新项目最新版 → §3.3 → 版本卡片 |
| 「在现有项目下加 light 主题」 | 生成 `light.html` → 与现有文件同 commit → 卡片吐主入口 |
| 「基于 V2 改标题」 / 「基于「{项目名}」V2版本进行编辑」 | §4.4 合并流程 → 版本卡片 |
| 用户给图（本地路径或工作区内文件） | `cp` → `assets/` → 对齐 HTML → Hard rule 2 校验 → 改代码则 §3.3 |
| 样式修改且未要求换图/删模块 | 改代码，**保留 assets 引用和文件** → §3.3 → 版本卡片 |
| 「恢复到 V2」 | §4.3 标准恢复（代码 + assets 一起回退）→ 版本卡片 |
| 小红书卡片 / 封面图 | 生成 HTML → 保存到项目 → export 出图到 `export/` → 同 commit → 双卡片（references/version-operations.md §4） |
| 小样阶段（「先出几个方向」） | `style-samples.html` 落项目目录（不 commit 不计版本号）→ 卡片供用户选择；重出方向递增 `style-samples-2.html` |
| 「帮我写一份方案」 | 不触发版本管理 |
| 指代不明 | 扫描 `我的项目/` → 追问 |
